1. Résumé exécutif

Le travail a porté sur deux axes. Le premier consistait à rendre A-CorePilot capable d’inventorier les objets Z/Y, d’exécuter ATC et de construire un graphe dont les compteurs sont traçables. Le second consistait à appliquer une démarche Clean Core à un report ALV existant sans modifier directement l’original.

  • Distinction entre un résultat where-used vide et une analyse échouée ou non supportée.
  • Provider ABAP autour de RS_EU_CROSSREF pour obtenir des callers identifiables.
  • Métriques du graphe calculées uniquement depuis les relations SAP_CROSSREF.
  • Résultats regex, ATC, ADT générique et LLM conservés comme candidats.
  • Classification R₅ déterministe, explicable et sans LLM.
  • Copie, stabilisation et refactorisation du report ALV.
  • Recherche d’APIs Released et confinement des accès fiscaux legacy derrière un wrapper.

2. Problèmes initiaux dans A-CorePilot

  • Des includes PROG/I affichaient zéro caller alors que leur programme principal les incluait.
  • Un zéro pouvait aussi représenter un appel SAP échoué ou une réponse inutilisable.
  • Des composants techniques de classes étaient comptés comme callers de leur propre classe.
  • Les relations incoming/outgoing ne correspondaient pas toujours à SAP GUI.
  • Le graphe pouvait sembler vide après navigation malgré sa persistance.
  • ATC sur près de cent objets rendait le scan long et vulnérable aux interruptions.
AffichageSignification adoptée
0La recherche SAP a réussi et aucune relation vérifiée n’a été trouvée.
—Valeur inconnue : type non supporté, appel échoué, réponse inutilisable ou scan non terminé.
n > 0Nombre d’objets utilisateurs uniques associés à des relations SAP vérifiées.
Principe : l’absence de preuve n’est pas une preuve d’absence. Un échec ne doit jamais être converti en zéro.

3. Provider ABAP de dépendances

Le where-used ADT générique n’étant pas cohérent pour tous les types techniques, une interface et une classe provider ont été créées côté SAP autour de RS_EU_CROSSREF.

A-CorePilot → /zacore/dependencies → ZCL_ACORE_DEPENDENCY_HTTP → ZCL_ACORE_DEPENDENCY_SAP → RS_EU_CROSSREF

L’interface ZIF_ACORE_DEPENDENCY_PROVIDER expose GET_USED_BY avec le nom et la classe de l’objet en entrée, puis les relations, le statut, le message et le compteur en sortie.

CALL FUNCTION 'RS_EU_CROSSREF'
  EXPORTING
    i_find_obj_cls = lv_object_class
    no_dialog      = 'X'
  TABLES
    i_findstrings  = lt_findstrings
    o_founds       = lt_founds.

Les résultats RSFINDLST sont normalisés, les préfixes comme \IC: sont retirés, puis les relations sont dédupliquées par source, cible, classes et nature. Le compteur est le nombre de sources uniques et non le nombre brut d’occurrences.

4. Graphe de dépendances fiable

CatégorieSourcesEffet
SAP VerifiedSAP_CROSSREFAlimente Where Used, Dependencies, Total Impact, Depth, cycles et chemins.
CandidateRegex, ATC, ADT générique, métadonnées ou LLMVisible sur demande, mais n’augmente aucun compteur de production.
  • Where Used / incoming : objets qui utilisent l’objet sélectionné.
  • Dependencies / outgoing : objets utilisés par l’objet sélectionné.
  • Total Impact : ensemble transitif des utilisateurs vérifiés susceptibles d’être affectés.

L’option Candidate edges est désactivée par défaut. Le cache et le graphe sont versionnés, écrits atomiquement et sauvegardés par checkpoints partial. Un seul scan peut fonctionner à la fois et les erreurs inattendues sont remontées dans l’interface.

5. Classification R₅ sans LLM

La classification LLM a été remplacée par des règles déterministes basées sur les métadonnées SAP, les findings ATC, le code ABAP et les conventions de nommage. Chaque décision conserve son type, sa confiance, sa source et sa preuve.

TypeExemples de preuveRisque

IMPLICIT_ENHANCEMENTMétadonnée/finding « implicit enhancement »0,85

La colonne R5 Type est disponible dans Object Inventory. Son infobulle affiche la provenance et la preuve.

8.2 Implémentation legacy

METHOD zif_yme_tax_provider~get_tax_data.
  CLEAR: ev_tax_account, ev_tax_rate,
         ev_account_found, ev_rate_found.

  SELECT SINGLE konts FROM t030k
    WHERE ktopl = 'MXCA' AND ktosl = 'VST'
      AND land1 = 'TN' AND mwskz = @iv_tax_code
    INTO @ev_tax_account.
  IF sy-subrc = 0. ev_account_found = abap_true. ENDIF.

  SELECT SINGLE knumh FROM a003
    WHERE kappl = 'TX' AND kschl = 'MWVS'
      AND aland = 'TN' AND mwskz = @iv_tax_code
    INTO @DATA(lv_knumh).
  IF sy-subrc <> 0. RETURN. ENDIF.

  SELECT SINGLE kbetr FROM konp
    WHERE knumh = @lv_knumh AND kopos = '01'
    INTO @DATA(lv_rate).
  IF sy-subrc = 0.
    ev_tax_rate = lv_rate / 10.
    ev_rate_found = abap_true.
  ENDIF.
ENDMETHOD.

  • La précision dépend des index cross-reference du système SAP.

A-CorePilot est une extension VS Code organisée en couches. Cette séparation évite que l’interface utilisateur connaisse les détails des protocoles SAP et permet de tester les règles métier indépendamment du webview.

13.1 Flux général d’un scan

  1. Lecture de l’hôte, du client et du nom utilisateur depuis les paramètres VS Code.
  2. Lecture du mot de passe depuis le stockage sécurisé.
  3. Ping de l’endpoint ADT afin de distinguer un problème de connexion d’une erreur d’analyse.
  4. Invalidation logique de l’ancien cache par création d’un checkpoint Discovery vide.
  5. Recherche des objets Z* et Y* des types PROG, CLAS, FUGR et INTF.
  6. Déduplication par type et nom.
  7. Limitation de l’échantillon à 100 objets pendant la phase de test.
  8. Enrichissement par petits lots pour protéger le système SAP.
  9. Appel du provider SAP pour les callers vérifiés.
  10. Lecture du source et calcul LOC lorsque le type le permet.
  11. Extraction des relations candidates depuis le source.
  12. Lecture de l’historique de modification lorsque l’objet possède un endpoint autonome.
  13. Construction et sauvegarde d’un premier graphe.
  14. Exécution ATC uniquement sur les objets autonomes.
  15. Enrichissement CRV lorsqu’un successeur est disponible.
  16. Calcul de la dette et de l’effort.
  17. Reconstruction du graphe avec les données finales.
  18. Écriture atomique du résultat complet et notification de l’interface.

16. Construction et métriques du graphe

16.1 Identité canonique

Un nœud est identifié par TYPE::NOM. Le type est ramené à sa base : PROG/P et PROG/I deviennent des nœuds de famille PROG, tout en conservant leur nature dans l’inventaire. Les noms sont trimés et convertis en majuscules.

16.2 Déduplication des arêtes

Une arête est identifiée par source, cible et nature. Lorsque plusieurs preuves décrivent la même relation, leurs sources et leurs extraits sont fusionnés. Si une preuve SAP_CROSSREF arrive après une candidate, elle devient la provenance principale et l’arête passe à l’état vérifié.

16.3 Formules des métriques

Where Used(X)   = nombre de sources uniques des arêtes vérifiées vers X
Dependencies(X) = nombre de cibles uniques des arêtes vérifiées depuis X
Impact(X)       = fermeture transitive inverse depuis X
Depth(X)        = plus longue profondeur vérifiée atteignable depuis X

Les cycles sont recherchés uniquement dans le sous-graphe vérifié. Cela empêche une simple occurrence regex de fabriquer un cycle de production.

16.4 Includes

Pour un report principal qui inclut TOP, SS et CLA, la direction correcte est :

ZCAP_1 --INCLUDES--> ZCAP_1_TOP
ZCAP_1 --INCLUDES--> ZCAP_1_SS
ZCAP_1 --INCLUDES--> ZCAP_1_CLA

Ainsi, chacun des includes possède un Where Used égal à un si le report parent est son seul utilisateur. Le report principal peut avoir zéro Where Used tout en possédant trois Dependencies : ces deux valeurs ne se contredisent pas.

17. ATC : exécution, performance et interprétation

ATC ne doit pas être exécuté séparément sur tous les sous-objets techniques lorsqu’ils sont déjà couverts par leur objet parent. Les sous-types I, S, M, F, K et J sont donc exclus de la liste des cibles autonomes.

  • Concurrence limitée à deux objets pour ATC.
  • Concurrence limitée à quatre objets pour l’enrichissement général.
  • Échec d’un objet isolé sans annuler automatiquement tous les autres.
  • Classification A/B/C/D seulement lorsque le résultat ATC est exploitable.
  • Une erreur ATC laisse la classification inconnue au lieu d’attribuer A.

18. Dette technique et effort

Le score composite est normalisé sur une échelle proche de 0 à 100. Il combine les findings ATC, la taille, la profondeur du graphe, le type de modification et l’âge de l’objet.

ATC normalisé    = min(1, pointsATC / 100)
LOC normalisé    = min(1, LOC / 2000)
Depth normalisé  = min(1, graphDepth / 10)
Age normalisé    = min(1, ageDays / 1825)

Debt = round(100 * (
  0.30 * ATC_normalisé +
  0.20 * LOC_normalisé +
  0.20 * Depth_normalisé +
  0.20 * ModType_multiplier +
  0.10 * Age_normalisé))

L’effort de base est de 1, 3, 8 ou 21 story points pour A, B, C ou D. Un multiplicateur dépendant de la profondeur, borné à deux, augmente l’effort des objets fortement couplés.

Gouvernance : ces coefficients sont des règles de priorisation du projet. Ils doivent être validés par l’entreprise avant d’être utilisés pour engager un budget ou décider automatiquement d’une migration.

19. R5 : règles, priorité et explicabilité

Le classifieur examine les preuves dans un ordre contrôlé. Une modification classique détectée par ATC est prioritaire. Viennent ensuite les enhancements explicites ou implicites, les BAdI, les wrappers et enfin le développement personnalisé par défaut.

if ATC says modified SAP standard -> CLASSICAL_MODIFICATION / high
else if exact implicit evidence   -> IMPLICIT_ENHANCEMENT / high
else if ENHANCEMENT-POINT         -> EXPLICIT_ENHANCEMENT / high
else if IF_EX_* or GET/CALL BADI  -> BADI_IMPLEMENTATION / high
else if ZCL_IM_* naming only      -> BADI_IMPLEMENTATION / medium
else if wrapper name + delegation -> WRAPPER_PROXY / high
else if Z/Y namespace             -> CUSTOM_DEVELOPMENT / medium
else                              -> CUSTOM_DEVELOPMENT / low

Les commentaires ABAP sont retirés avant l’analyse afin qu’un exemple commenté ne déclenche pas une classification. Une syntaxe ENHANCEMENT ambiguë ne permet pas d’inventer si le hook est implicite ou explicite : elle reçoit une confiance faible.

22.3 Enrichissement

METHOD enrich_data.
  LOOP AT mt_result ASSIGNING FIELD-SYMBOL(<result>).
    IF <result>-tax_code IS INITIAL.
      CONTINUE.
    ENDIF.
    mo_tax_provider->get_tax_data(
      EXPORTING
        iv_tax_code       = <result>-tax_code
      IMPORTING
        ev_tax_account    = <result>-tax_account
        ev_tax_rate       = <result>-tax_rate
        ev_account_found  = DATA(lv_account_found)
        ev_rate_found     = DATA(lv_rate_found) ).
  ENDLOOP.
ENDMETHOD.

23. Analyse des SELECT SINGLE

Le finding « SELECT SINGLE is possibly not unique » signifie que le prédicat ne couvre pas une clé unique. Il ne faut pas le masquer sans règle métier.

SituationCorrection
La clé complète est connueAjouter tous les champs de clé au WHERE.
Plusieurs lignes sont métierment possiblesLire la liste et traiter explicitement la cardinalité.
Une seule ligne doit être choisieSELECT UP TO 1 ROWS avec ORDER BY déterministe.
Lecture répétée dans LOOPPrécharger par lots ou joindre via une source Released adaptée.

Dans le wrapper fiscal, la sélection doit également considérer les dates de validité si elles appartiennent réellement à la source utilisée. L’erreur rencontrée sur DATAB a montré qu’il ne faut jamais supposer qu’un champ existe dans A003 sans vérifier le dictionnaire du système.

26. Checklist de mise en production

26.1 Sécurité

  • Protéger l’endpoint /zacore/dependencies par authentification et autorisations adaptées.
  • Ne jamais journaliser les mots de passe ou secrets SAP.
  • Utiliser HTTPS avec un certificat reconnu.
  • Limiter l’accès Repository selon les rôles de l’utilisateur technique.
  • Tracer les erreurs sans exposer le source ABAP sensible.

26.2 Performance

  • Valider les limites de concurrence avec l’équipe Basis.
  • Mesurer le temps moyen et le taux d’échec sur un package pilote.
  • Prévoir reprise, timeout, backoff et cache selon la charge.
  • Éviter ATC complet synchrone pour des milliers d’objets.
  • Prévoir scan incrémental par date ou transport.

26.3 Qualité des données

  • Afficher date, système, client et version du scan.
  • Ne mélanger ni environnements ni clients SAP dans le même cache.
  • Conserver la provenance de chaque arête.
  • Auditer un échantillon contre SAP GUI.
  • Définir un seuil de couverture avant usage décisionnel.

26.4 Transport et gouvernance

  • Déplacer les objets depuis $TMP vers un package transportable.
  • Créer une demande dédiée et documentée.
  • Séparer objets backend SAP, extension VS Code et configuration.
  • Faire valider le wrapper legacy par l’architecture Clean Core.
  • Créer une date de révision pour chaque exception non Released.

29. Conclusion

A-CorePilot est passé d’un prototype aux compteurs difficiles à interpréter vers une chaîne où la provenance des relations est visible et où seules les preuves SAP vérifiées influencent les métriques. L’exercice ALV a appliqué une migration progressive : préserver l’original, stabiliser une copie, corriger les problèmes, rechercher et tester les APIs Released, puis isoler la dette non remplaçable.

Le résultat n’est pas présenté comme une conformité Clean Core absolue. Il constitue une base auditable, testable et évolutive dont les limites sont documentées.
